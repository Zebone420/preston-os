========================================================
ROOT CAUSE
========================================================
The production runtime is seeded with a HUMAN-OWNER Supabase session
(owner refresh token -> persisted, auto-refreshed). That standing
owner session confers FULL owner authority - including the sole
approval-decision RPC - to unattended host processes and to anything
that can read the host session store. The approval gate is therefore
NOT bound to a live human; it is satisfied by a machine-held owner
credential. A node process bearing that host-origin owner session
decided apr-df39913f at 23:40:34.

RESIDUAL ATTRIBUTION UNCERTAINTY (stated honestly): the exact node
process is not nameable from retained logs - no deployed service,
executor, SSH, cron, or MCP was running at 23:40:34, and the gateway
log keeps no source IP. The two remaining possibilities, which the
evidence cannot separate, are (a) an ad-hoc/transient node invocation
on the host that left no systemd/cron/SSH trace, or (b) off-host use
of a copied owner ACCESS token (bearer) from the runtime session -
which would still log as user_agent node with no IP. OWNER INPUT
NEEDED: did any owner-side tool (phone automation, a saved script, or
a ChatGPT-side integration) hold an owner Supabase session and issue
this decision? Either way the fix below closes both.

========================================================
BLAST RADIUS
========================================================
Because is_owner() is the ONLY check and the runtime session passes
it, that session can decide (approve OR reject) ANY pending production
approval - not just this workflow - and can submit owner goals and
write any owner-RLS-gated table. This is full standing owner authority
on an unattended host.
